# Jarvis dashboard

The web dashboard: sign in with a passkey, run workspaces with their members, store the workspace's provider keys, and pair iPhones.

```
browser ──HTTPS──▶ Next.js (pages + server actions) ──gRPC + mTLS──▶ Vault      provider keys
                         │   spiffe://jarvis.local/dashboard-api  ──▶ app API    pairing codes, phone sessions
                         └──▶ PostgreSQL `dashboard`: users, passkeys, sessions, workspaces, members, invitations
```

The Next.js server is the dashboard's backend. Towards the services it is `dashboard-api`, and each service's policy allows it only what the dashboard needs. For example, the Vault allows it to store, list and revoke keys, but never to read them back. The browser never talks to a service directly.

| Path              | What                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------- |
| `src/app/`        | Pages (server components)                                                                 |
| `src/actions/`    | Server actions: the only way the browser changes anything                                 |
| `src/components/` | Client components (forms, passkey prompts) and presentational pieces                      |
| `src/server/`     | Server only: configuration, database, sessions and passkeys, access checks, gRPC clients  |
| `src/proxy.ts`    | Content-Security-Policy with a nonce per request, HSTS                                    |
| `tests/`, `e2e/`  | Vitest (unit and PostgreSQL integration), Playwright (browser, against the running stack) |

Protobuf types come from [`gen/ts`](../../gen/ts/) (`@jarvis/proto`, generated by `pnpm nx run proto:generate`).

## Accounts and workspaces

- **Passkeys only.** An account is a name and one or more passkeys (Face ID, Touch ID, a security key); there is no password.
  - Passkeys are discoverable and always ask for user verification, so signing in needs no user name.
  - Each passkey is stored as its public key. Its WebAuthn user handle is random, not the user id.
- **Recovery codes.** Signing up gives 10 single-use codes (60 bits each, stored as SHA-256 hashes), shown once.
  - A code signs in to a session that can only add a new passkey.
  - Codes can be replaced from the account page.
- **Sessions** are random 256-bit tokens in an HttpOnly cookie, stored hashed.
  - The cookie is `__Host-` prefixed and Secure over https.
  - A session ends after 24 hours unused or 7 days at most, on sign-out, or when you sign out your other browsers.
  - Every sign-in starts a fresh token.
- **Workspaces** are the services' tenants: a workspace id is the `tenant_id` of its keys, phones and conversations.
  - **Owners** manage keys, members and invitations.
  - **Members** use Jarvis with the workspace's keys and see them (metadata only).
  - A workspace always keeps an owner. The check locks the memberships, so two owners stepping down at once cannot both succeed.
- **Invitations** are single-use links, valid for 7 days, stored hashed and shown once. The invitee signs in or creates an account, and joins with the invitation's role.
- **Phones** belong to the person who paired them: the Devices page shows and signs out only yours.

## Protections

- **Every server action checks the session and the caller's role itself;** a hidden button is not the protection. Someone outside a workspace gets "not found", so workspace ids cannot be probed.
- **CSRF:** Next.js refuses server actions whose `Origin` is not the dashboard's. Cookies are `SameSite=Lax`, and the WebAuthn challenge cookie is `Strict`.
- **WebAuthn challenges** are single use, valid for 5 minutes, and bound to the browser that asked for them (an HttpOnly cookie).
- **Content-Security-Policy:**
  - scripts only with the request's nonce (`strict-dynamic`), and no `unsafe-eval` in production,
  - `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`,
  - plus `nosniff`, `Referrer-Policy: same-origin`, and a Permissions-Policy that allows only WebAuthn.
- **Provider keys** go from the form to the Vault once, over mTLS. The dashboard keeps no copy: it zeroes its buffer after the call, and never logs requests. Only the last four characters come back.
- **Rate limits:** starting passkey ceremonies is limited to 30 a minute, and recovery codes to 5 tries every 5 minutes.
- **Errors:** users see what they can act on. Anything unexpected is logged, and the user gets a short reference to quote.
- **Logs** are JSON (pino). They hold ids, never tokens, codes or keys, and route patterns rather than paths (invitation links carry their token).

## Configuration

| Variable                                                      | Default           |                                                                                             |
| ------------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------- |
| `DASHBOARD_ORIGIN`                                            | required          | Where browsers reach it, e.g. `https://jarvis.example.com`; `http` only for `localhost`     |
| `DASHBOARD_RP_ID`                                             | the origin's host | WebAuthn relying party: the host or a parent domain. Changing it invalidates every passkey. |
| `DASHBOARD_RP_NAME`                                           | `Jarvis`          | Shown in passkey prompts                                                                    |
| `DASHBOARD_DATABASE_URL` or `DASHBOARD_DATABASE_URL_FILE`     | required          | PostgreSQL; migrations run at startup                                                       |
| `DASHBOARD_TLS_CA`, `DASHBOARD_TLS_CERT`, `DASHBOARD_TLS_KEY` | required          | Its identity towards the services: `spiffe://jarvis.local/dashboard-api`                    |
| `DASHBOARD_VAULT_ADDR`                                        | `127.0.0.1:50051` |                                                                                             |
| `DASHBOARD_APP_ADMIN_ADDR`                                    | `127.0.0.1:50055` | The app API's admin (gRPC) listener                                                         |
| `DASHBOARD_SESSION_IDLE`, `DASHBOARD_SESSION_LIFETIME`        | `24h`, `7d`       |                                                                                             |
| `DASHBOARD_TRUST_PROXY`                                       | `false`           | Rate-limit by the first `X-Forwarded-For` address (only behind a proxy you control)         |
| `LOG_LEVEL`                                                   | `info`            |                                                                                             |
| `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`                          |                   | Set it to the same value on every instance when running several                             |

A wrong configuration stops the server at startup, and the error names every problem (never the values).

`GET /api/health` answers `200` when the dashboard reaches its database.

## Development

```bash
tools/dev-stack.sh up             # the whole stack, dashboard included: http://localhost:3000
pnpm nx run dashboard:serve       # or just the dashboard (needs the Vault, the app API and PostgreSQL)
```

`scripts/dev-run.sh` takes:

- the `dashboard-api` certificate from the Vault's development CA,
- the database password from `deploy/compose/.env` (database `dashboard`, created by `pnpm infra:up`).

To try it with the fake providers:

1. Create an account and a workspace.
2. Store `sk-dev-fake-0001` as the OpenAI key; the fake voice and LLM providers accept only that one.
3. Pair the iPhone from **Devices**.

Passkeys need a secure context: `http://localhost` works, and any other host needs https. To use it from other devices, serve it through Tailscale and set the origin accordingly:

```bash
tailscale serve --bg --https=8444 http://127.0.0.1:3000
DASHBOARD_ORIGIN=https://<mac>.<tailnet>.ts.net:8444 tools/dev-stack.sh up
```

Passkeys are bound to the host, so passkeys made on `localhost` do not work on the `ts.net` address, and the other way round.

## Tests

```bash
pnpm nx run dashboard:test   # Vitest: unit tests, and integration tests with PostgreSQL (testcontainers, needs Docker)
pnpm nx run dashboard:lint   # ESLint + TypeScript
pnpm nx run dashboard:e2e    # Playwright in Chrome, against the running stack (tools/dev-stack.sh up)
```

- **Unit:** ids, recovery codes and their typing, configuration checks, rate limits, the CSP, safe redirects.
- **Store:**
  - sessions (idle and lifetime expiry, "sign out other browsers"),
  - single-use challenges, recovery codes, keeping the last passkey,
  - a workspace always keeping an owner, including a deterministic race of two owners stepping down,
  - invitations (single use, expiry, withdrawal, other workspaces).
- **Sign-in:** recovery sessions limited to adding a passkey, a fresh session on every sign-in, forged cookies, challenge use from another browser, rate limits, and role checks on the server.
- **gRPC:** the clients against fake Vault and app API servers over real mTLS: their certificate, request ids, key rotation that asks first, error mapping, and a service that is down.
- **End to end,** in Chrome with a virtual authenticator, against the real Vault and app API:
  - sign up, store and rotate a key, revoke it as leaked,
  - pair a phone, invite a member who signs up with their own passkey,
  - the member's limits, removing them,
  - sign out and in, and recovery on a new device.
  - The run leaves an `E2E …` workspace, with its keys revoked, in the development database.

Mutation testing confirmed that the tests catch these defects:

- no owner check in actions,
- members removing others,
- no lock in the last-owner check,
- a session kept across sign-ins,
- challenges usable for another ceremony,
- no idle timeout.

## Known limitations

- **Coming next:** MCP connections (4.2b) and the audit trail (4.2c).
- **Not yet:**
  - renaming or deleting a workspace,
  - renaming passkeys,
  - listing Mac daemons (registered with `orchctl`),
  - email (invitations are links to send yourself).
- **Rate limits are per instance,** in memory.
- **The services trust `dashboard-api` for every tenant.** The dashboard checks membership before each call; the services do not see the user.
